Basics

Files can be tracked or untracked.
Tracked files can be : unmodified, modified, or staged (staging area also called the index)

git status

git add : to stage (add to the index) new files
git add .           # stage all the files of current dir
git add dirname     # stage all the files of a directory
git add -A          # equivalent of hg addremove

# If a file is staged with git add, then modified again : it will be modified AND staged ;
# the next commit will record the version of the file when git add was called.
# To record its last state, run git add again on the file.

git commit -m "my message" - will record the staged changes.
git commit -a automatically stages every file that is already tracked before doing the commit ; permits to skip the git add part

git checkout tags/version-3.1

git rm <file> : removes file from tracked files and from the filesystem
If file is staged, need to do git rm -f <file>
git rm --cached <file> untracks a staged file without deleting it from the filesystem 
glob patterns available in rm - but git does its own filename expansion => escape : git rm log/\*.log

git mv README.txt README equivalent to mv README.txt README ; git rm README.txt ; git add README

git clone --depth=1 <url>
Creates a shallow clone. These clones truncate the commit history to reduce the clone size. This creates some unexpected behavior issues, limiting which Git commands are possible. These clones also put undue stress on later fetches, so they are strongly discouraged for developer use. They are helpful for some build environments where the repository will be deleted after a single build.

git clone --filter=blob:none <url>
Creates a blobless clone. These clones download all reachable commits and trees while fetching blobs on-demand. These clones are best for developers and build environments that span multiple builds.

git clone --filter=tree:0 <url>
Creates a treeless clone. These clones download all reachable commits while fetching trees and blobs on-demand. These clones are best for build environments where the repository will be deleted after a single build, but you still need access to commit history.

.gitignore

- Blank lines or lines starting with # are ignored.
- Standard glob patterns work.
- You can end patterns with a forward slash (/) to specify a directory.
- You can negate a pattern by starting it with an exclamation point (!).

Reset, revert, amend

# Oh shit, I committed and immediately realized I need to make changes!
git add .       # or add individual files
# overrides last commit, and uses current state of staging area to perform the new commit
git commit --amend
git commit --amend --no-edit

# Change last commit message
git commit --amend -m "initial commit"

Then change commit in editor
if already pushed : git push origin main --force

# Unstage, remove from the index, without doing anything else:
git reset
git reset <file>

# Throw away all uncommitted changes in the working directory, restore to last commit
# WRANING, NOT RECOVERABLE - cannot be done on a particular file
git reset --hard

# Throw away uncommitted changes on a file
git checkout -- <file>

Change previous commit message

git rebase -i HEAD~X
# X is the number of commits to go back
# Move to the line of your commit, change pick into edit,
# then change your commit message:
git commit --amend
# Finish the rebase with:
git rebase --continue

Rebase opened your history and let you pick what to change. With edit you tell you want to change the message.
Git moves you to a new branch to let you --amend the message.
git rebase --continue puts you back in your previous branch with the message changed.

# Unstaging a staged file
git reset HEAD <file>

Reverting a file to last commit - WARNING : unrecoverable
git checkout -- <file>

# Modify 3 last commits
git rebase -i HEAD~3
# this edits .git/refs/git-rebase-todo
# change the commit messages and replace 'pick' by 'reword' or other command, save and quit 
git rebase --continue
git push --force-with-lease

See also http://git-scm.com/book/fr/v2/Git-Tools-Rewriting-History

git clone --bare my_project my_project.git
scp -r my_project.git user@git.example.com:/opt/git
# At this point, other users who have SSH access to the same server which has read-access to the /opt/git directory can clone your repository by running

Squashing

# Convert 30 commits of branch toto in a single commit 
git reset --soft $(git merge-base main toto)
git commit -m "My unique commit message"
# git merge-base finds the common ancestor to main and toto
# git reset --soft <commit-id> brings back the branch toto at this common commit, keeping all the changes in the staging area.

# start a branch from main branch
git co main && git pull     # to be sure that main is up to date
git co my-branch
# squash commits of my-branch since it was created from main
git reset --soft $(git merge-base main HEAD)

HEAD                    names the commit on which you based the changes in the working tree.
FETCH_HEAD              records the branch which you fetched from a remote repository with your last git fetch invocation.
ORIG_HEAD               is created by commands that move your HEAD in a drastic way (git am, git merge, git rebase, git reset),
                        to record the position of the HEAD before their operation, so that you can easily change the tip
                        of the branch back to the state before you ran them.
MERGE_HEAD              records the commit(s) which you are merging into your branch when you run git merge.
REBASE_HEAD             during a rebase, records the commit at which the operation is currently stopped, either because of conflicts or an edit command in an interactive rebase.
REVERT_HEAD             records the commit which you are reverting when you run git revert.
CHERRY_PICK_HEAD        records the commit which you are cherry-picking when you run git cherry-pick.
BISECT_HEAD             records the current commit to be tested when you run git bisect --no-checkout.
AUTO_MERGE              records a tree object corresponding to the state the ort merge strategy wrote to the working tree when a merge operation resulted in conflicts.

@                       shortcut for HEAD
[<refname>]@{<date>}    e.g. master@{yesterday}, HEAD@{5 minutes ago} HEAD@{1979-02-26 18:30:00}
<refname>@{<n>}         n-th prior value of that ref. e.g. master@{1}
@{<n>}                  reflog entry of the current branch.

<rev>                   Include commits that are reachable from <rev> (i.e. <rev> and its ancestors).
^<rev>                  Exclude commits that are reachable from <rev> (i.e. <rev> and its ancestors).
<rev1>..<rev2>          Include commits that are reachable from <rev2> but exclude those that are reachable from <rev1>.
                        When either <rev1> or <rev2> is omitted, it defaults to HEAD.
<rev1>...<rev2>         Include commits that are reachable from either <rev1> or <rev2> but exclude those that are reachable from both.
                        When either <rev1> or <rev2> is omitted, it defaults to HEAD.
<rev>^@, e.g. HEAD^@    A suffix ^ followed by an at sign is the same as listing all parents of <rev>
                        (meaning, include anything reachable from its parents, but not the commit itself).
<rev>^!, e.g. HEAD^!    A suffix ^ followed by an exclamation mark is the same as giving commit <rev> and all its parents prefixed with ^ to exclude them (and their ancestors).
<rev>^-<n>              e.g. HEAD^-, HEAD^-2    Equivalent to <rev>^<n>..<rev>, with <n> = 1 if not given.
